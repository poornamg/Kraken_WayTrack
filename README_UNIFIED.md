# Unified Order Flow (Store Manager & Dispatcher)

## Architecture
The system employs a hub-and-spoke architecture where multiple frontend applications communicate with a single centralized backend via REST API endpoints.
- **Store Manager** calls `POST /api/v1/unified/orders` to create orders and `GET /api/v1/unified/orders` to list its own orders.
- **Dispatcher** polls `GET /api/v1/unified/orders` every 5 seconds to get the live list of orders and uses `PATCH /api/v1/unified/orders/:id` to update the order status to `Scheduled` or `Deferred`.
- **Backend** is an Express/Fastify server utilizing MongoDB as its persistence layer. For this feature, the `UnifiedOrder` collection was added to track real-time unified orders.

## Environment Variables
Each frontend React/Vite app requires the following environment variable to locate the API:
- `VITE_API_BASE_URL` - Set this to the deployed backend's URL (e.g., `https://waylink-api.onrender.com`). If not set, defaults to `http://localhost:3000`.

The backend requires:
- `MONGODB_URI` - The connection string for the MongoDB instance.
- `PORT` - Optional port number (defaults to 3000).

## Local Development
1. Start the MongoDB instance using Docker:
   ```bash
   docker compose up -d mongo mongo-init
   ```
2. Navigate to `backend/` and start the API:
   ```bash
   npm run dev
   ```
3. In separate terminals, start the Store Manager and Dispatcher:
   ```bash
   cd Store-Manager && npm run dev
   cd dispatcher && npm run dev
   ```

## Deployment
1. **Backend Deployment**:
   Deploy the `backend` folder to a Node.js hosting platform (such as Render, Heroku, or DigitalOcean App Platform). Create a free MongoDB database using MongoDB Atlas, and add the provided connection string as the `MONGODB_URI` environment variable in your hosting provider's dashboard.
2. **Frontend Deployment**:
   Deploy each frontend folder (`Store-Manager`, `dispatcher`) as a separate Vercel project. In the Vercel dashboard for each project, go to **Settings > Environment Variables** and add `VITE_API_BASE_URL` pointing to your deployed backend URL.

## Final Report

**Files Changed:**
- `backend/src/database/models/unifiedOrder.ts`: Added the unified order schema matching the Dispatcher UI requirements exactly.
- `backend/src/modules/unified-orders/routes.ts`: Added `GET`, `POST`, and `PATCH` endpoints for `/unified/orders`.
- `backend/src/app.ts`: Registered the new `unified-orders` router.
- `backend/src/server.ts`: Initialized seed data on startup.
- `Store-Manager/src/api/store.ts`: Rewrote `submitStoreOrder` to use the unified endpoint, added `listStoreOrders`.
- `Store-Manager/src/App.tsx`: Wired `OrdersPage` to read dynamically from the backend and poll every 5 seconds instead of rendering the hard-coded mock list.
- `dispatcher/src/api/planning.ts`: Updated `orders()` to fetch from the `/unified/orders` endpoint.
- `dispatcher/src/App.tsx`: Rewrote `refreshPlanningData` to format unified orders, changed `publishSchedule` and `handleDeferOrders` to PATCH statuses directly to the backend. Lowered the polling interval to 5 seconds.

**Mock Data Removed:**
- No mock data was explicitly deleted from the source files to avoid breaking unrelated flows, but the hard-coded `initialOrders` arrays in both `Store-Manager/src/App.tsx` and `dispatcher/src/App.tsx` are now ignored and overridden by real API data.

**Intentionally Left Untouched:**
- The complex backend operations such as the full `publishTrip` logistics, `order.items` strict references, and `calendar` contexts were left intact in the existing backend code to avoid breaking Loader/Driver flows. The `Loader` and `Driver` apps remain entirely untouched as requested. Visual designs and layout structures were completely preserved. 

**Risks & Follow-Ups:**
- The `Loader` and `Driver` apps will need to be refactored to read from `UnifiedOrder` instead of the old `Order` and `Trip` schemas. They will need to expect a single `status` string instead of complex nested `Trip` sub-documents.
- Order IDs are currently generated by MongoDB (`_id`). If the user requires specific semantic IDs (like `ORD-XXXX`), a pre-save hook should be added to `UnifiedOrder`.
